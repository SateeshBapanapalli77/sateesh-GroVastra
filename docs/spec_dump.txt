What "one template or message" means
Each due campaign step sends one selected message to one eligible customer. A campaign may
enroll many customers and contain several scheduled steps. This does not reduce the project to a manual
single-message sending screen.

This v2 specification supersedes the earlier sender-focused handoff. WhatsApp is the only delivery channel
in this release. Most of the work described here is campaign logic; template approval and account approval
are explicitly excluded.

Release decisions
- Provide preset-driven campaigns with a finite sequence of 1-3 steps. A general visual workflow builder and
arbitrary user code are not required.
- Support annual date triggers, explicit event/season dates, domain-event triggers and inactivity scans.
- Use approved-template messages for automated outbound campaigns. Custom free-text editing is not a
campaign-template approval bypass.
- Published campaign versions are immutable. Existing enrollments retain their version; current opt-out,
stock, order and provider state are always rechecked.
- Use a MongoDB-backed scheduler and durable worker jobs. A MongoDB replica set supports the specified
transactions. Redis is not required.
- No bulk WhatsApp request is assumed: fan out safely to one execution per customer per campaign step.
Terms
Campaign: saved rules and steps. Occurrence: one birthday year, collection launch, enquiry or other
trigger instance. Enrollment: one customer participating in that occurrence. Execution: one planned
message step. Attempt: one provider submission for an execution. These are distinct records and metrics.

Version contract
Save edits to a draft with expectedVersion. Activation freezes an immutable campaignVersion and records
activatedBy, activatedAt, reviewFingerprint and nextEvaluationAt. Editing an active campaign creates
another draft; publishing affects only new enrollments by default.
Existing enrollments keep the trigger, sequence, audience snapshot and timezone they were created with.
Live permission, customer deletion, stock, order state, global pause and template usability override every
version.
End and archive
The configured endAt stops new enrollments and expires steps beyond the campaign deadline. Archive also
cancels remaining unsubmitted work and preserves history. Neither operation recalls messages already
accepted by the provider. Treat accepted and outcome-unknown executions conservatively.

07 / CUSTOMER SELECTION
Audience logic and eligibility
Select eligible customers automatically. Use a controlled rules language, not arbitrary MongoDB filters or
JavaScript from React. Every query includes tenant and permitted branch scope.
{
  "all": [
    {"field": "customer.status", "op": "eq", "value": "ACTIVE"},
    {"field": "preferences.weave", "op": "in", "value": ["silk"]}
  ],
  "any": [
    {"field": "preferences.budgetMaxPaise", "op": "gte",
     "value": 600000},
    {"field": "tags", "op": "contains", "value": "occasionwear"}
  ],
  "none": [
    {"field": "serviceIssueOpen", "op": "eq", "value": true}
  ]
}
Semantics: all predicates must pass; any is optional but at least one must pass when present; none
predicates must all fail. Missing fields fail ordinary comparisons. Empty any/none are neutral. An entirely
empty audience is invalid unless the owner explicitly selects ALL_ELIGIBLE.
Mandatory gates outside the editable audience
- Valid, active customer and destination; marketing permission for promotional steps; channel suppression
always respected.
- Required trigger data and business eligibility, such as a valid occasion date or unresolved enquiry.
- No duplicate enrollment for the same occurrence; no duplicate destination contact when household
records overlap.
- Permission and current business conditions are checked again when each step becomes due.
Store a concise match explanation, such as "birthday in 14 days; opted in; silk preference". Do not infer
religion, relationship status, birthday or partner contact details. Unsupported fields/operators fail validation
rather than broadening the audience.

enrollment per campaign/customer/occurrence and one execution per stable step. Changing a template or

EXAMPLE operations: plan every 15 minutes; claim due steps every minute; reconcile data nightly. Discover
occasion dates from today minus the largest positive step offset through today plus the largest lead time
plus 30 days. This includes future D+7 steps for a recently passed occasion. Reconcile existing active
enrollments independently of that window. Never use one setTimeout per future message.
For an existing enrollment, load its pinned campaignVersionId before upserting its stable steps. Never add steps from the
newest active version to an older enrollment. Use bounded cursor batches and durable checkpoints.
Time conversion
For a date trigger: resolve occurrence local date, add signed calendar-day offset, apply the step local time,
then convert with the campaign IANA timezone to UTC. Store original local date/time/zone and resolved
dueAt. For an event delay, add elapsed duration to authoritative occurredAt, then fit the result into

local time. Feb 29 uses the selected annual policy. Date-only birthdays must never be converted through
midnight UTC.
Late work
Normal activation/import and explicit resume use FUTURE_ONLY: elapsed steps are logged as skipped.
EXAMPLE technical-outage grace is 2 hours, bounded by expiresAt, send hours and current relevance.
Longer outages skip obsolete steps; never replay a backlog in a burst. A future optional greeting can still run
after a missed invitation.
Set expiresAt to the earliest applicable step lateness cutoff, campaign end and source latestUsefulAt. Moving a send into
allowed hours cannot extend that deadline. A staff conversation hold is not a technical outage and does not earn catch-up

Deterministic collision resolution
Before dispatch, lock/arbitrate by tenant + canonical destination. Among currently due eligible marketing

 Action / change
Required engine behaviour
Pause campaign / global pause

Reschedule appointment

New customer destination

Transactional boundaries
1. Publish campaign version and change activeVersionId atomically. 2. For large event fan-outs, commit
each bounded batch's enrollment/step effects with its cursor; mark the event processed only after the final
batch. Replay resumes the cursor. 3. At submission, validate control generations, reserve capacity, freeze

[D1, D2]
Claims and control generations
